## 0. 定位与红线

**定位**：SOL 版 = 游客可完整游玩的单机防守游戏 + 可选钱包连接 + USDC/SOL 内购 + 成就徽章。链上部分是**增强层**，不是游玩门槛。

**红线（不因任何版本计划变更）**：

1. **赌场与真钱完全隔离**：内购得来的金币**永不进入赌场**。实现口径——一期赌场未开放、保持关闭；二期赌场上线时只用**独立免费筹码**（每日免费发放定量、不可购买、不可兑换、与金币零互通），从机制上切断「真钱→金币→赌场」通路。不存在「只用金币下注所以没事」的说法，金币可真钱买到即构成通路。
2. **不发自有代币**。代币奖励/发币是独立一条线（经济模型＋合规＋流动性），不在本设计内，要做另行拍板。
3. **私钥零接触**：游戏永不索要、永不接触助记词与私钥；所有签名都在用户钱包 App 内经 MWA 完成。UI 须常置一行明示：「本游戏永不索要助记词/私钥」。
4. **收款用专用钱包**，与发布者钱包（@musen123）、交易钱包、主钱包全部隔离；客户端只内置收款**地址**（公开信息）。
5. **主网交易开关由用户拍板才开**。设计、测试网联调不等于授权主网收钱。
6. **游客默认**：不连钱包全程可玩、无功能阉割；链上功能不可用时灰置，不弹窗骚扰。

## 1. 总体架构

组件（全部在既有栈内，不新增常驻服务于一期）：

| 组件 | 角色 |
|---|---|
| Godot 客户端 | 游戏本体＋链上模块（连接/支付/查单/发货） |
| Solana SDK（GDExtension，版本锁定见 §2） | WalletAdapter（Android MWA）、RPC 客户端、转账构造、SPL 接口 |
| 用户钱包 App（Phantom 等） | MWA 对端：授权、签名、发送，全在钱包内完成 |
| Solana RPC（**双运营方**） | 查余额、查交易；验单结论须两家一致（见 §4.3） |
| 收款钱包（专用，新建）＋其 USDC ATA | 内购收款；私钥由用户保管，游戏侧只认地址 |
| 轻后端（二期可选） | 订单复验、限购服务端计数、徽章代铸、设备级对账；一期不建 |

三条数据流：

- **连接流**：游戏 → MWA authorize → 钱包回地址 → 游戏查余额展示。全程只读。
- **支付流**：游戏生成订单并**先落盘** → 构造转账（收款 ATA＋金额＋memo 订单号）→ MWA 拉起钱包签名发送 → 拿到 signature **立即落盘** → 双 RPC 校验完整验单谓词 → finalized 后发货（幂等）。
- **徽章流（二期）**：达成成就 → 铸 cNFT 到玩家地址（代铸走后端，或玩家钱包自付铸造，二期定）→ 游戏内展示。后端不存在时成就只记链下。

**冒烟门（P0，devnet，Seeker 真机，全过才进 P1）**：

## 3. 钱包接入设计

- **入口**：主界面与设置页各一个「连接钱包」按钮；HUD 不常驻钱包信息，避免遮挡战斗画面。
- **状态机**：未连接（游客）→ 连接中 → 已连接（显示短地址 `D5Gw…bbCE` 式＋SOL/USDC 余额）。断开、超时、被拒都回落未连接并给一句人话提示。
- **绑定**：连接成功后把地址写入存档头 `wallet_address`。换一个钱包地址连接时，明示「将切换到该地址的权益记录」，不自动合并两边权益。
- **降级**：设备无钱包 App、用户拒绝、断网——链上入口灰置并标注原因，其余玩法零影响。
- **一期（P1）只读**：只做 authorize＋查余额＋绑档，不发起任何交易。交易能力随内购阶段（P2）才进包。

**总量闸**：资源类 SKU（gold_s＋gold_l）每日合计上限 **4,900 金**（3×800＋2,500），约 9.8 本单属性书——这是「买便利」的上限口径，超过即是买通关，不卖。

**资源生命周期（v2 明确）**：金币/木材是**本局资源**（每局重开清零），内购资源不做永久货币。发放方式：在局内购买即时入本局账；局外（主菜单）购买记「待领」，下一局开局自动入账并在开局结算行明示。月卡每日领取同此口径。英雄解锁与皮肤是**永久权益**（绑钱包地址，见 §9-6）。

**月卡规则（v2 明确）**：有效期＝购买 finalized 之时起 30×24 小时；每日可领窗口按 UTC+8 自然日切分，每日 00:00 后可领当日 300 金；**漏领不补**；有效期内不可叠加购买，到期后可续购；到期日与已领日期记入权益记录。

### 4.2 订单状态机与支付流程

**订单状态机（v2 新增，全程本地账本驱动）**：

`CREATED`（已生成、已落盘，未付款）→ `SUBMITTED`（已取得 signature 并落盘）→ `CONFIRMED`（链上 confirmed，UI 只显示「处理中」）→ `VERIFIED`（finalized 且验单谓词全过）→ `DELIVERED`（已发货，幂等键＝signature）。
失败/挂起分支：`EXPIRED`（报价或 blockhash 过期且未付款，作废、须重建订单）、`UNKNOWN`（已提交但超时未见链上结果，**不等于失败**，进复查队列）、`FAILED_TX`（链上 meta.err≠null，确定失败、不发货）、`DISPUTED`（双 RPC 结论分歧，挂起人工处理）。

**原子落盘纪律**：订单在**送签之前**先落盘（临时文件写完＋rename 原子替换，防写一半被杀进程留下半条记录）；signature 一拿到**立即落盘再开始轮询**。任何时刻杀进程重启，账本状态自洽、可续查。

**支付流程**：

1. 玩家在商店「充值」页选 SKU，客户端做**二次确认弹窗**（商品、数量、折合价、收款方短地址，明示链上付款不可自动退款）。
2. 生成订单：`order_id`＝128 位随机数；含 SKU、币种、锁定金额（**以最小单位整数存储，禁浮点**：USDC 6 位小数，$0.99＝990000）、付款方地址、创建时间、状态=`CREATED`；落盘。
3. **有效期管理**：SOL 计价订单的锁定汇率有效期 **5 分钟**，过期订单转 `EXPIRED`、重建新单；交易的 recent blockhash 有效期约 60–90 秒，构造后须立即送签，超时**重建交易**（新 blockhash、同一 order_id），**绝不因 90 秒没查到确认就判定失败或引导重付**——查不到先转 `UNKNOWN` 复查。
4. **付款前检查**：付款方 USDC 余额 ≥ 订单额、且 SOL 余额 ≥ 0.01（网络费），任一不足则付款钮灰置并明示缺什么。
5. 构造转账（USDC 走 §4.3 的 ATA 口径；SOL 走 SystemProgram transfer），附 memo=`JG:<order_id>`；过指令白名单校验（§7）后经 MWA 拉起钱包。**玩家拒绝/关钱包 → 订单回 `CREATED` 可重付或作废，不发货。**
6. 取得 signature → 立即落盘、状态=`SUBMITTED` → 双 RPC 轮询：confirmed 转 `CONFIRMED`（只显示处理中）；finalized 后执行完整验单谓词（§4.3），全过转 `VERIFIED` 并发货转 `DELIVERED`；meta.err≠null 转 `FAILED_TX`；超时未见结果转 `UNKNOWN`。
7. UI 反馈到账内容；订单账本永久保留，供对账与查单补发。

**掉单恢复（v2 重写）**：`UNKNOWN`/`SUBMITTED`/`CONFIRMED` 订单在每次启动与进商店时自动复查，验过即补发（幂等键 signature，重复查不重复发）。**signature 从未落盘的极端情形**（拿到 signature 前被杀进程）：按**收款地址交易历史**扫描——付款方地址＋金额＋memo `JG:<order_id>` 三项匹配到链上成功交易且未履约的，认领并补发。memo 只是认领线索，**不是付款凭证**，认领后仍须走完整验单谓词。

### 4.3 验单谓词、ATA 与发货门槛

**固定参数（写死进客户端常量，双人核对）**：

| 参数 | 值 |
|---|---|
| USDC mint（主网官方） | `EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v` |
| Token Program | `TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA` |
| USDC decimals | 6（金额一律整数最小单位） |
| 收款方 | 专用收款钱包地址＋其 **USDC ATA 地址**（双内置、双核对） |

**ATA 前置（v2 新增）**：USDC 付款的目标是收款方的 **ATA（Associated Token Account）**，不是钱包主地址。主网上线（P3）前须由用户在 Phantom 侧确认收款钱包的 USDC ATA **已创建**（收过一次 USDC 即存在），并在客户端内置该 ATA 地址；验单时核对交易中 token account 的 owner＝收款钱包、mint＝官方 USDC。devnet 阶段用 devnet 测试 mint 全链演练，参数表另列、不与主网混用。

**完整验单谓词（六项全过才算有效付款，缺一不可）**：

1. **集群正确**：交易所在集群与订单币种网络一致（devnet 的单在主网验单一律拒）。
2. **交易成功**：`meta.err == null`。带正确地址/金额/memo 的**失败交易不算付款**。
3. **实际转账成立**：解析交易指令——USDC 须为 SPL Token transfer/transferChecked，源＝付款方 ATA、目标＝收款方 ATA、mint＝官方 USDC、金额（最小单位整数）＝订单锁定值；SOL 须为 SystemProgram transfer，目标＝收款地址、lamports＝订单锁定值。
4. **订单归属**：memo 指令内容严格等于 `JG:<order_id>`，且该 order_id 是本设备账本内未履约订单。
5. **付款方一致**：交易 fee payer / 转账源 owner ＝订单绑定的钱包地址。
6. **未曾履约**：该 signature 不在已发货记录内（幂等）。

**发货门槛**：`confirmed` 只作「处理中」显示，**`finalized` 且谓词全过才正式发货**。（代价是多等约十几秒，换掉回滚风险，不接受「小额先发」。）

**RPC 交叉核对**：验单结论须**两家不同运营方** RPC（如付费节点＋公共节点）各查一遍且一致；仅换同一家的节点列表不算交叉核对。两家分歧 → 订单转 `DISPUTED` 挂起，不发货、告警人工处理。

### 4.4 发货校验两档与对账口径

- **A 档·客户端校验（一期）**：客户端按 §4.3 验单。能防误付、付错金额、失败交易冒充、重复发货与一般篡改；防不住改包伪造。单机游戏一期接受，理由：伪造发货的收益仅限自家单机存档，无交易对手受损。
- **B 档·轻后端校验（二期，视收入决定）**：服务器复验交易、存订单库、限购服务端计数、出对账报表，并承接徽章代铸。收入没起来之前不养这个服务。
- **对账（一期口径降实）**：一期只能做**链上收款核账＋人工补单**——每日脚本拉收款钱包/ATA 当日入账流水，与「应收清单」（由已发货订单的 signature 汇总，人工导出）比对笔数与金额，对不上就告警、人工处理。**明示局限**：公链只能证明「钱到了」，证明不了某台具体设备是否已发货；设备级对账要等 B 档。v1 写的「账本比对」在一期没有设备侧数据源，不冒充。

### 4.5 退款与误付

链上转账**不可逆**，无自动退款。二次确认弹窗＋金额锁定＋付款前余额检查是第一道防线；真发生误付（付错金额、重复付款），玩家凭 signature 走店铺既有客服通道人工处理。若人工判定退款，对应订单权益**回收/作废**并在账本标记，口径随客服话术在上线前一并定版，本设计不预设自动规则。

### 4.6 收款钱包

新建专用收款钱包（与发布者钱包、ORE 交易钱包、主钱包隔离）。助记词由用户在 Phantom 内新建并自行保管，游戏侧只需要收款**地址**与 **USDC ATA 地址**。客户端内置前做双人核对（一人写、一人读）防写错一位——地址错一位，钱进黑洞。主网首笔真单必须小额且人工确认到账地址无误（见 §8 P3）。

## 5. 其他链上元素

- **成就徽章（cNFT，二期）**：节点＝通关 20 波、四圣兽方位集齐并激活、无伤守核通关、上方谷终局完成。用压缩 NFT。**成本口径修正（v2）**：cNFT 铸造**并非天然依赖后端**——可由铸造权限方后端代铸，也可设计为玩家钱包自付铸造；单枚成本随 Merkle tree 占用与网络费浮动，**不是固定单价**，二期立项时按当时树深与费率实测再定。徽章与 B 档绑定只是 v1 的选择，二期时两条路一并评估。
- **存档上链：不做**。成本、隐私、延迟都不划算；地址绑定已满足换设备认档的需求锚点（存档本体仍走本地/云文件）。
- **排行榜：链下做**。上链排行榜是为不存在的作弊对抗付真实成本，不做。
- **英雄/皮肤 NFT 化：后置**。需要转移、交易、版税与市场对接，是独立产品线；本设计只保证皮肤 SKU 的权益记录结构将来可迁移。

## 6. 存档与数据变更

存档新增字段（老存档缺字段一律按游客/未购/未领处理，向前兼容）：

- `wallet_address`：绑定地址（空=游客）
- `orders[]`：订单账本（order_id、signature、SKU、币种、金额最小单位整数、付款方地址、**状态机状态**、时间、复查次数）
- `entitlements`：永久权益（英雄解锁位、已购皮肤、月卡到期日与已领日期、资源包当日已购计数与日期）
- `pending_grants[]`：局外购买的待领资源（下一局开局入账后清除）
- `badges_claimed[]`：二期徽章领取记录

**签名切换迁移（v2 新增）**：调试签名包与 release 签名包**不能覆盖安装**。P1 切 release 线时须走迁移流程：旧包内导出存档文件 → 卸载旧包 → 装 release 包 → 导入存档；keystore 文件与证书指纹**离机备份＋校验**列入 P1 验收（keystore 丢失＝该游戏永远无法更新，等同事故）。

## 7. 安全与风险清单

| 风险 | 缓解 |
|---|---|
| SDK 未审计/被篡改依赖 | 只用标准转账；**指令白名单**：客户端只允许 SystemProgram transfer、SPL Token transfer/transferChecked、Memo 三类指令，送签前逐条校验每条指令的 program id、目标地址与金额与订单一致，白名单外指令一律拒绝送签（收款钱包隔离保护不了玩家，玩家侧靠此条）；依赖锁定版本＋校验和，升级依赖走重审 |
| 改包伪造发货 | 一期接受（单机、无对手方受损）；收入起来上 B 档后端复验 |
| SOL 计价波动/拉价失败 | USDC 为主计价；报价 5 分钟有效期；拉价失败时 SOL 选项灰置，只开放 USDC |
| 收款地址/ATA 写错 | 双内置双人核对＋首笔真单小额人工确认到账 |
| 付款方无 SOL 付网络费 | 付款前检查 SOL ≥ 0.01，不足灰置并明示 |
| 玩家被钓鱼索要助记词 | UI 常置明示；官方渠道外任何「客服」索要助记词均为诈骗，写进商店页文案 |
| RPC 限流/不稳/单家欺骗 | 双运营方交叉核对；分歧挂起；`UNKNOWN` 状态保证不丢单、不误判失败 |
| 改时钟/回档绕限购 | 一期接受并明示；月卡时间源用链上时间；B 档改服务端计数 |

| 阶段 | 内容 | 验收标准 |
|---|---|---|
